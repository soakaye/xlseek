# Research & Technical Decisions: UI項目調整 (UI Adjustments)

## 概要
本ドキュメントは、Excel Grep アプリケーションのUI項目調整（IME変換確定Enter誤爆防止、フォルダ入力欄のEnter無効化、ステータスバー進捗表示の改善、周辺セルプレビューグリッドの縦横固定見出し・スクロール検証）における技術的背景、意思決定、および代替案の比較検討をまとめたものである。

---

## 決定事項 1: 日本語入力(IME)確定時の Enter キー制御方式

### 課題
macOS (WebKit / Safari / WKWebView) および Chromium 環境において、日本語IMEによる漢字・仮名変換確定のEnterキー押下時に、検索が意図せず発火（誤爆）してしまう問題。

### 決定事項
`compositionstart` / `compositionend` イベントリスナーによるIME入力状態のフラグ追跡と、`compositionend` 発火直後（50ms以内）のタイムスタンプ照合、および `e.nativeEvent.isComposing` / `e.keyCode === 229` の複合判定を採用する。

```javascript
if (e.isComposing || isComposing || e.keyCode === 229) return;
if (Date.now() - lastCompositionEndTime < 50) return;
if (e.key === "Enter") {
  startSearch();
}
```

### 根拠
- Chromium では Enter 確定時に `keydown`（`isComposing: true`）→ `compositionend` の順で発火するが、WebKit (macOS Safari / Tauri WKWebView) では `compositionend` が `keydown`（`isComposing: false`）よりも先行して発火する。
- 単純な `!e.isComposing` のチェックだけでは WebKit 環境で Enter 確定時の `keydown` を防げないため、`Date.now() - lastCompositionEndTime < 50` のディレイガードが不可欠である。

### 検討した代替案
- **keyup イベントでの検索発火**: keydown ではなく keyup で Enter を検知する案。しかし keyup は IME 確定後の Enter リリース時にも発火するため、依然として誤爆が発生し却下。
- **Form の onSubmit 依存**: `<form>` の submit イベントに委ねる案。WebKit での Enter 確定時 submit 発火制御がブラウザ差異に依存し、クロスプラットフォームで確実性を欠くため却下。

## 決定事項 2: フォルダ入力欄での Enter キー挙動

### 課題
フォルダ入力欄にフォーカスがある状態で Enter を押した際に検索が走る挙動はユーザーのメンタルモデルに反し、パス入力中の誤検索を招く。

### 決定事項
フォルダ入力欄での Enter キー押下による検索実行を完全に排除する。IME変換確定中は変換確定処理をそのまま通し、非IME時の Enter キー押下は `e.preventDefault()` により無効化（無視）して、入力欄内のフォーカスを維持する。

### 根拠
- フォルダ入力は検索条件のセットアップであり、検索実行トリガー（キーワード確定やSEARCHボタン押下）と明確に分離すべきである。
- Enterキーで意図しない検索が走るフラストレーションをゼロにし、入力フォーカスを維持することで連続入力・編集を妨げない。

### 検討した代替案
- **Enter押下でキーワード欄へフォーカス移動**: 一見便利に見えるが、ユーザーがまだフォルダパスを修正したい場合に勝手にフォーカスが奪われストレスとなるため却下。デフォルトのテキスト入力挙動（フォーカス維持）が最も自然である。

## 決定事項 3: ステータスバー進捗バーの配置とフェーズ可視化

### 課題
プログレスバーがステータスメッセージの右側にあると、メッセージの長さ変動でバーの位置が揺れ動き、さらに大容量フォルダ探索時にファイル解析が始まるまでUIが停止しているように見える。

### 決定事項
- プログレスバーをステータスメッセージの手前（左側）に固定幅（`w-44` / 176px）で配置する。
- 検索処理を「探索中（フォルダスキャン中アニメーション・対象フォルダパス表示）」と「ファイル解析中（%・件数・ファイル名）」の2フェーズに明確に分離して表示する。
- 不要な内部エンジン名称（Calamine Engine）の常時表示を撤去し、領域を実用情報に割り当てる。

### 根拠
- プログレスバーの位置が固定されることで視線移動が安定し、進捗確認の視認性が飛躍的に向上する。
- フォルダ走査の開始が100ms以内にフィードバックされるため、アプリの応答性が高く感じられる。

## 決定事項 4: 周辺セルプレビューの Freeze Panes（固定見出し）と双方向スクロール

### 課題
周辺セルプレビュー領域において、親コンテナの `overflow-hidden` による横スクロール遮断を解消しつつ、縦スクロール時にも列見出しを見失わないExcelライクな表示が求められた。

### 決定事項
- 単一のスクロールコンテナ（`overflow-auto`）内に CSS `position: sticky` を用いた固定見出し構造を実装する。
  - `#` 行見出し（左上角）: `sticky top-0 left-0 z-30`
  - 列見出し（A, B, C...）: `sticky top-0 z-20`
  - 行番号列: `sticky left-0 z-10`
- テーブル境界線は `border-collapse: separate; border-spacing: 0;` で定義し、sticky要素の境界線ちらつきを防止。
- スタンドアローンHTMLモックにおいて、標準ビューポート（高さ420px）で縦スクロールが確実に発生するよう、最低30行以上のサンプルデータを確保する。

### 根拠
- 2重スクロールバーや複雑なJSスクロール同期プラグインを避け、ネイティブの `position: sticky` だけで滑らかな60fpsスクロールと固定見出しを実現。
- モックデータに十分な行数があることで、UIレビューおよび実機確認がブラウザ単体で即座に完結する。
