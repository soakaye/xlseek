## User Scenarios & Testing *(mandatory)*

### User Story 1 - Standalone xlseek-mcp Binary for MCP Clients (Priority: P1) 🎯 MVP

As a developer or AI practitioner using Model Context Protocol (MCP) clients (such as Claude Desktop, Cursor, or CLI agents),
I want to download a pre-built, platform-native standalone executable of `xlseek-mcp` directly from GitHub Releases,
So that I can configure and run the Excel search MCP server immediately without having to install the full desktop GUI application or build Rust from source.

**Why this priority**:
Currently, `publish-to-auto-release.yml` only uploads Tauri desktop application installers (`.msi`, `.dmg`, `.deb`). Users who purely need the headless MCP server for Claude Desktop or Cursor cannot easily obtain the standalone binary without building from source or extracting it from installed app directories. Delivering individual standalone binaries directly fulfills the core user need.

**Independent Test**:
Download the standalone `xlseek-mcp` release asset for the host platform from GitHub Releases, grant execution permissions if needed, configure it in an MCP client configuration (e.g. `claude_desktop_config.json`), and verify that the MCP server starts up, initializes via stdio, and successfully lists and executes the `search_excel` tool.

**Acceptance Scenarios**:

1. **Given** a new version tag (e.g., `v1.2.0`) pushed to GitHub, **When** the release workflow completes, **Then** individual standalone `xlseek-mcp` binary assets for supported operating systems are attached to the GitHub Release.
2. **Given** a downloaded `xlseek-mcp` binary on a target machine, **When** executed with `--help` or launched by an MCP client via stdio, **Then** it starts immediately without requiring external runtime dependencies or Tauri GUI libraries.

### User Story 2 - Multi-Platform Distribution for macOS, Linux, and Windows (Priority: P2)

As a cross-platform user running macOS, Linux, or Windows,
I want `xlseek-mcp` release assets tailored to my operating system and architecture,
So that I can run the MCP server natively with maximum performance and minimal setup friction.

**Why this priority**:
MCP clients and developer environments run across Windows, macOS (Apple Silicon and Intel), and Linux. Providing pre-built binaries across standard platforms ensures accessibility for the entire user base.

**Independent Test**:
Inspect the GitHub Release assets generated by the workflow and verify that distinct executables or archives exist for all targeted platform triples (e.g., macOS ARM64, Linux x86_64, Windows x86_64).

**Acceptance Scenarios**:

1. **Given** a release workflow run, **When** artifacts are uploaded, **Then** each supported target platform has a corresponding distinct `xlseek-mcp` asset clearly identifying its OS and architecture.
2. **Given** a Windows user, **When** downloading the Windows asset, **Then** the executable has the `.exe` extension and executes properly on 64-bit Windows environments.

### User Story 3 - Robust Automated Release Pipeline (Priority: P3)

As a project maintainer creating a release via `npm version` and git tag push,
I want the GitHub Actions release workflow to compile and upload `xlseek-mcp` binaries reliably and idempotently alongside GUI desktop bundles,
So that releases require zero manual build or upload intervention.

**Why this priority**:
Release automation prevents human error, ensures build reproducibility across clean CI environments, and reduces maintenance burden.

**Independent Test**:
Trigger the workflow via a release tag event in GitHub Actions and verify that all build steps succeed and assets are attached to the release without collision or permission errors.

**Acceptance Scenarios**:

1. **Given** a pushed tag matching `v*`, **When** the release workflow triggers, **Then** the release job builds `crates/mcp` in release mode (`--release`) for each target.
2. **Given** draft release creation by Tauri action or release step, **When** `xlseek-mcp` assets are uploaded, **Then** existing draft release metadata and other assets are preserved.

---

### Edge Cases

- What happens if a platform build fails during the matrix run?
  - `fail-fast: false` should be maintained so that remaining platform builds continue and upload their respective assets even if one runner fails.
- What happens if an asset with the same name already exists in the draft release?
  - The upload step must support replacement/clobbering to prevent workflow failures upon re-runs.
- What happens with executable permissions on Unix systems (macOS/Linux)?
  - Distributed as an archive (`.tar.gz`), executable permissions (`chmod +x`) are preserved inside the tarball so users can run the binary immediately after extraction.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Workflow MUST build the `xlseek-mcp` binary (`crates/mcp`) in `--release` mode for each designated target platform when triggered by a version tag (`v*`).
- **FR-002**: Supported platform matrix MUST cover macOS Apple Silicon (`aarch64-apple-darwin` on `macos-latest`), Linux x86_64 (`x86_64-unknown-linux-gnu` on `ubuntu-24.04`), and Windows x86_64 (`x86_64-pc-windows-msvc` on `windows-latest`).
- **FR-003**: Release asset packaging format MUST be a compressed archive containing the standalone executable: `.tar.gz` for macOS/Linux (preserving executable permissions) and `.zip` for Windows, following the naming pattern `xlseek-mcp-<tag>-<target-triple>.<ext>`.
- **FR-004**: Release workflow MUST implement a dedicated independent matrix job (`publish-mcp-binaries`) in `.github/workflows/publish-to-auto-release.yml`, decoupled from the Tauri GUI desktop bundle build.
- **FR-005**: All generated `xlseek-mcp` release assets MUST be uploaded and attached to the GitHub Release corresponding to the triggering tag (`github.ref_name`) using `gh release upload --clobber` or equivalent GitHub Release action.
- **FR-006**: The workflow MUST utilize `GITHUB_TOKEN` with necessary write permissions (`contents: write`) to upload release assets without requiring external secret tokens.
- **FR-007**: Workflow configuration MUST maintain clean documentation, clear step names, and descriptive comments in accordance with project standards.

### Key Entities *(include if feature involves data)*

- **Release Asset**: The distributable file (`.tar.gz` or `.zip`) attached to a GitHub Release, containing the standalone `xlseek-mcp` executable and labeled with version tag and target triple.
- **Target Triple**: The Rust target specification (`x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`) defining the compilation environment.
- **GitHub Release**: The draft or published release entry created on the repository associated with a specific git version tag.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of defined target platforms (macOS Apple Silicon, Linux x86_64, Windows x86_64) have corresponding `xlseek-mcp` release archive assets attached to the GitHub Release upon tag push.
- **SC-002**: Standalone `xlseek-mcp` binaries compile and run without external desktop GUI library dependencies (e.g., zero GTK/WebKit dependencies on Linux).
- **SC-003**: Standalone `xlseek-mcp` binary archive extraction and initial stdio handshake test completes in under 30 seconds on a clean target machine.
- **SC-004**: Release workflow execution completes with zero fatal errors on all enabled matrix platforms in GitHub Actions.

## Assumptions

- Tag push events matching `v*` will remain the standard release trigger.
- The `xlseek-mcp` crate in `crates/mcp` compiles as a self-contained command-line executable via standard `cargo build --release -p xlseek-mcp --target <target>`.
- GitHub Actions runners (`windows-latest`, `macos-latest`, `ubuntu-24.04`) have standard Rust toolchains and network access to download dependencies from crates.io.
- The release entry is created or updated by either `publish-tauri` or `gh release upload` (using `--clobber`), ensuring assets from both jobs coexist on the same release tag.
