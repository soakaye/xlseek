## User Scenarios & Testing *(mandatory)*

### User Story 1 - 大規模ディレクトリにおける検索開始および初回結果表示の即時化 (Priority: P1)

利用者が大量のファイルや深い階層を持つフォルダを指定して検索を開始した際、従来の「全フォルダの走査完了を待ってから検索を開始する」挙動を解消し、フォルダ内のファイル検出とファイル内容の検索を並行して行う。これにより、検索開始直後から見つかったファイルの内容検索が即時に開始され、最初の検索結果（ヒット項目）が速やかに画面に表示される。

**Why this priority**: 多数のExcelファイルが存在する環境（大規模プロジェクト、共有フォルダ、階層の深いアーカイブなど）において、ユーザーが検索結果を得られるまでの待ち時間（初回結果表示時間: Time-to-First-Result）を最小化し、アプリケーションの体感速度と作業効率を大幅に高めるため。

**Independent Test**: 数千ファイル以上が存在するディレクトリを対象に検索を実行し、全ファイル走査の完了を待つことなく、ファイル発見と同時に検索結果がインクリメンタルに画面上に表示され始めることを確認する。

**Acceptance Scenarios**:

1. **Given** 多数のサブフォルダやExcelファイルを含むディレクトリが検索対象として指定されているとき、**When** 利用者が検索開始ボタンを押下したとき、**Then** 全ファイルの一覧取得完了を待たずに即座にファイル内容の検索が開始され、ヒットしたセルがリアルタイムに結果リストへ表示される。
2. **Given** 検索処理が実行中であるとき、**When** 新たな対象ファイルがバックグラウンドで継続的に検出されている最中であっても、**Then** すでに検出されたファイルに対するセル内容走査が途切れることなく進行し、UIのステータス表示が動的に更新される。
3. **Given** 走査対象ディレクトリ内に少数のファイルしか存在しないとき（単一フォルダや数個のファイル）、**When** 検索を実行したとき、**Then** オーバーヘッドなく即座に全走査と検索が完了し、正確な結果が表示される。

### User Story 2 - ディレクトリ走査中および検索中の即時キャンセルと高応答性 (Priority: P1)

利用者が誤ったフォルダを選択したり検索条件を間違えた際、または探していた目的の結果が既に見つかって検索を途中で止めたい場合に、「中止（キャンセル）」ボタンをクリックすると、たとえ巨大なディレクトリツリーを走査中であっても直ちに処理が中断され、UIが即座に入力待機（再検索可能）状態に戻る。

**Why this priority**: 巨大ディレクトリや低速なネットワークドライブでの走査中にキャンセルを押しても処理が止まらずアプリが待たされる現象を完全に解消し、ユーザーがストレスなくいつでも操作を中断・やり直せる操作応答性を保証するため。

**Independent Test**: 数万件のファイルが存在する巨大フォルダを対象に検索を開始し、開始直後（ディレクトリ走査が進行中の段階）にキャンセルボタンをクリックした際、1秒未満で即座に走査および検索処理が完全停止し、キャンセル完了のステータスに切り替わることを確認する。

**Acceptance Scenarios**:

1. **Given** 巨大なディレクトリの走査が行われている最中であるとき、**When** 利用者がキャンセルボタンをクリックしたとき、**Then** ディレクトリの巡回およびファイルの検索処理が即座に中断され、ステータスバーにキャンセル状態が表示されて新たな検索の実行が可能になる。
2. **Given** 検索実行中にすでにいくつかの結果がヒットしているとき、**When** キャンセルボタンをクリックしたとき、**Then** 中断時点までに発見された検索結果はそのままリスト上に維持され、走査処理のみが安全に即時停止する。
3. **Given** 検索開始直後（0.1秒以内）にキャンセル操作が行われたとき、**When** 中断要求が処理されたとき、**Then** システムがフリーズしたりエラー状態に陥ることなく、安全に待機状態へ戻る。

### User Story 3 - 並行走査時における正確かつ直感的な進捗状況の可視化 (Priority: P2)

ファイルの検出と内容検索が同時に行われている間、利用者はステータスバーを通じて、現在何個のファイルが走査済みであるか、現在どのファイルを検査中であるか、何件の一致が見つかったかをリアルタイムに把握できる。ファイル全体の検出完了後は、全体の分母に対する正確な進捗率が表示される。

**Why this priority**: 並行処理中であってもバックグラウンドの動作状況をユーザーに分かりやすくフィードバックし、システムが正常に動作している安心感を提供するため。

**Independent Test**: 長時間の検索を実行した際、ステータスバーにおいて走査済みファイル数とヒット件数が滑らかにカウントアップされ、全体の検出完了前後で適切な進捗表示が維持されることを確認する。

**Acceptance Scenarios**:

1. **Given** ファイル検出と検索が並行して実行されているとき、**When** 利用者が画面下部のステータスバーを確認したとき、**Then** 走査済みファイル数、ヒット件数、および現在処理中のファイル名が一定頻度でリアルタイムに更新表示され、全対象ファイル検出前はプログレスバーが検出中アニメーションおよび走査済ファイル数を表示する。
2. **Given** ディレクトリ内の全対象ファイルの検出が完了したとき、**When** 検索処理が継続しているとき、**Then** 確定した全体ファイル数（分母）と走査済みファイル数（分子）に基づく正確なパーセンテージ（進捗バー）表示へとスムーズに切り替わる。
3. **Given** 検索が正常に終了したとき、**When** 最終結果が表示されたとき、**Then** 最終的な走査ファイル数、総ヒット件数、および所要時間がステータスバーに正しく表示される。

### Edge Cases

- **対象ディレクトリが空または対象拡張子のファイルが1件も存在しない場合**: ファイル走査が無駄に待機することなく即座に「0ファイル走査、0件一致」で正常完了すること。
- **対象ディレクトリに膨大なファイル（10万件以上）が存在する場合**: メモリ消費量が過剰に増大することなく、発見されたファイルから順次ストリーミング方式で検索が消化され、安定して動作すること。
- **深いネスト（数十階層）やアクセス権限のないサブディレクトリが含まれる場合**: アクセス権限のないフォルダでエラーが発生しても処理全体が異常終了せず、スキップして残りのフォルダ走査とファイル検索を継続すること。
- **検索開始直後の超高速キャンセル（レースコンディション）**: 走査処理と検索処理の双方が安全に即時終了し、リソースリークやプロセスの取り残しが発生しないこと。
- **ディレクトリ走査の完了より先にファイルの検索が完了する場合（少数ファイル）**: ファイル検索側が不自然に待機することなく、走査完了とともに速やかに全処理の完了へ移行すること。
- **一時ファイル（`~$` で始まるExcelロックファイル等）が大量に存在する場合**: 走査段階で即座に除外され、検索キューに不要なファイルが投入されないこと。

## Requirements *(mandatory)*

### Out of Scope

- **ファイルシステム監視による常駐インデックス作成**: あらかじめファイルシステムの変更を監視してインデックス（常駐型データベース）を構築しておくキャッシュエンジン機能は対象外とする（オンデマンドのリアルタイム走査とする）。
- **外部クラウドストレージ独自API連携**: ローカルマウントされていないクラウドストレージ（SharePoint APIやOneDrive API等）への独自REST APIによる走査は対象外とする（OSのローカルファイルシステムとしてアクセス可能なパスのみを対象とする）。

### Functional Requirements

- **FR-001**: システムは、指定された検索対象ディレクトリ内のファイル検出処理と、検出されたファイルに対するExcelセル内容検索処理をシーケンシャル（全件走査完了待ち）ではなく、パイプライン並行処理として同時に実行しなければならない（MUST）。
- **FR-002**: システムは、ディレクトリ走査によって検索対象の拡張子に合致するファイルが見つかり次第、全ファイルの一覧化完了を待たずに即時に対象ファイルを検索処理キューへ供給し、検索を開始しなければならない（MUST）。
- **FR-003**: システムは、ディレクトリ走査処理中においてもキャンセル要求を常時監視し、キャンセル指示が発行された場合は直ちにディレクトリの再帰走査を中断して終了しなければならない（MUST）。
- **FR-004**: システムは、検索キャンセル要求を受信した際、ディレクトリ走査およびファイル内容検索の双方を遅延なく（1秒以内に）安全に停止させ、アプリケーションを即座に再検索可能なアイドル状態へ復帰させなければならない（MUST）。
- **FR-005**: システムは、検索途中でキャンセルされた場合であっても、中断時点までに発見された検索結果の一致アイテムを破棄せず、UIの結果テーブル上に保持しなければならない（MUST）。
- **FR-006**: システムは、一時ファイル（`~$` で始まるExcelロックファイル等）を走査段階で確実に除外し、検索パイプラインへ供給してはならない（MUST）。
- **FR-007**: システムは、ファイル検出および検索が進行中の間、走査済みファイル数、発見された一致件数、現在検査中のファイル情報を含む進捗状況を一定間隔（50ms以上）で滑らかにUIへ通知しなければならない（MUST）。この際、全対象ファイルの検出が完了するまでの間は総ファイル数を未確定（0）として扱い、検出完了後に確定した総ファイル数を通知して正規の進捗率（パーセンテージ）表示へと移行しなければならない（MUST）。
- **FR-008**: システムは、読み取り権限のないフォルダや破損ファイルに遭遇した場合でも走査を中断せず、エラーを安全にスキップして他の有効なファイルの検出および検索を継続しなければならない（MUST）。

### Key Entities

- **検索パイプライン (Search Pipeline)**: ディレクトリ探索による対象ファイル検出器（プロデューサー）と、検出されたファイルのExcelブック解析器（コンシューマー）を接続する並行処理機構。
- **スキャン進捗 (Scan Progress)**: 走査済みファイル数、総ファイル数（確定後は全件数）、ヒット件数、現在走査中ファイル、経過時間、スキャン状態（Scanning, Completed, Cancelled, Error）を保持する進捗モデル。
- **キャンセル信号 (Cancellation Signal)**: ディレクトリ巡回および全並行ワーカーに対して即時停止を通知するスレッドセーフなフラグ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 10,000件以上のファイルを含むディレクトリにおいて、検索開始から最初の検索結果（または最初のファイル検査開始）が表示されるまでの時間（Time-to-First-Result / TTFR）が、全件走査完了を待つ従来方式と比較して 80% 以上短縮されること。
- **SC-002**: 任意の規模のディレクトリ走査中において、利用者が「キャンセル」ボタンを押下してから検索処理が完全停止しUIが操作可能になるまでの応答時間が 1.0 秒以内（95%以上のケースで 500ms 以内）であること。
- **SC-003**: 並行走査および検索の実行中において、UIスレッドが一切ブロック（描画フリーズ）せず、ウィンドウの移動やリサイズがスムーズに行えること。
- **SC-004**: 検索結果の整合性（ヒット件数、一致セル内容、行・列情報）が、従来のシーケンシャル走査方式と完全に一致し、検出漏れや重複が 0 件であること。

## Assumptions

- 探索対象のファイルシステムは、ローカルディスク（SSD/HDD）またはOSから標準ファイルパスとしてマウントされたネットワークドライブであること。
- 同時に開くファイルハンドルの数は、OSの上限（ulimit / ハンドル制限）を超えないよう適切に制御されること。
- 既存のフロントエンド進捗表示インターフェース（`ScanProgress` 型および `StatusBar`）の基本構造を活用し、後方互換性を維持すること。
